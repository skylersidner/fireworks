**`fireworks.reduceFlashing.v1` (new key): clean.** `readChoice` accepts only `'on'` or `'off'`, and anything else reads as "follow the OS". The value decides one boolean in the visitor's own render quality. It is never sent, never rendered and never part of a document. Only same-origin script can write it, so a tampered value only affects the visitor's own playback. `fireworks.flashNotice.v1` treats any non-null value as dismissed, which is the same self-only trust.

## C3 verdict: partial isolation is acceptable for Phase 5

**Accepted, severity low, not a gate blocker.** Before Phase 8, an attacker does control the names in these sentences, because every interim visitor's `/mine` lists every saved creation. But the unisolated spots can't spoof a decision:
- Every action is a separate element with fixed text: the dialog buttons, Remix, Delete, and the save status buttons. Bidi reordering doesn't cross element (paragraph) boundaries, so a U+202E name can't relabel a button.
- The name sits inside curly quotes, and the dialog title is only `Delete “{name}”?`. The worst case is a scrambled tail of one sentence. For example, in `confirmLinkBody` a name can reverse the trailing "Display settings stay as they are." That is cosmetic. It doesn't change what Cancel or Open does.
- The surfaces where a name stands alone next to controls (the player heading next to Remix, cards next to Play, Share and Delete, the player notice) are isolated. That is the case C3 was written for.

**Recommended cheap close (hardening, Luigi):** wrap the name in U+2068 FIRST STRONG ISOLATE … U+2069 POP DIRECTIONAL ISOLATE inside `quoted()` (`save-copy.ts`) and the inline `“${name}”` sites (`mine-page.ts` `deleteTitle` and `afterDelete`, `designer-copy.ts` `confirmLinkTitle` and `confirmLinkBody`, and `creationTitle` in `link-copy.ts`). These are plain strings, so they isolate in toasts, dialogs and `document.title` with no template change. Copy specs that compare exact strings would need the marks.

## Findings

**F1 [low] `src/web/fireworks-web/src/app/unsafe-sinks.spec.ts:39,73`: the C1 and C2 guards miss two Angular spellings.** Measured by adding each line to `player-page.html` and running the spec (restored afterwards and byte-compared):
- `<span [innerHtml]="p.name">`: the spec passes 7/7. Angular's compiler remaps `innerHtml` to the `innerHTML` property (`@angular/compiler` 22.2.6, `DOM_PROPERTY_REMAPPING`). Angular's sanitizer would strip handlers, but markup injection (links, styled fake UI) would reach every viewer of a link, and the ban is the only guard.
- `<a href="{{ p.name }}">`: the C2 test passes. Interpolated attribute bindings aren't matched.

No shipped file does either today, so this is a verifier defect, not a live XSS. **Fix (whoever owns the spec next, not Luigi alone):** make the HTML sinks case-insensitive (`/inner\s*html|outer\s*html/i` alongside the rest), match `(href|src|routerLink|formAction|xlink:href)="[^"]*\{\{[^}]*\bname\b` too, and add both strings to the negative-control list. Optionally ban `new Text(` and `BitmapText` under `src/engine` for the C2 canvas clause.

**F2 [low → accepted] C3 partial isolation.** The verdict and recommended close are above.

**F3 [info] `features/designer/shared/designer-draft.ts:134` together with `pages/designer-page/designer-save.ts` `save()`.** `readSource` accepts `kind: 'show'` in the shell designer's draft. A tampered draft with a show `source` makes `planSave` throw synchronously, after `this.saving.set(choice)`, so Save stays at "Saving…" until reload. Only same-origin script or the visitor's own devtools can do this (`/c/` never hands the designer a show). It is robustness, not security. Fix: the shell draft's `readSource` requires `kind === 'shell'`, or `save()` sets `saving` after `planSave` succeeds.

**F4 [info] Raw API responses are trusted as typed for display fields.** In `mine-page.ts` `toCard`, `item.palette` is assumed to be an array. `sourceFrom` copies `updatedAt` and `name` unvalidated, but `readSource` re-checks them on reload. Only the same-origin API can supply these values, and each failure mode is a render error, not an injection. No action needed before Phase 8.
