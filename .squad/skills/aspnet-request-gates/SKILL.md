# ASP.NET Core request gates: what the attribute seems to do vs. what it does

Use this when reviewing or building a route constraint, a content-type gate or a body-size limit in the Fireworks API (or any ASP.NET Core app with a catch-all route). Measured on .NET 11, Kestrel, 2026-11-13 (`boo-phase4-security-requirements.md`).

## Traps (each was measured)
1. **`{x:regex(...)}` is case-insensitive.** ASP.NET builds the constraint with `IgnoreCase | CultureInvariant`, so `[A-HJ-NP-Za-km-z]` also admits `l`, `I`, `O` and the Kelvin sign U+212A (as `k`). For a case-sensitive alphabet, write an `IRouteConstraint` that checks each char ordinally, and register it by name. Also anchor with `\z`, never `$`: `$` matches before a final `\n`.
2. **`[Consumes]` is an endpoint selector, not a 415 gate.** If any other endpoint can match (here `app.Map("/api/{**rest}")`), a wrong `Content-Type` routes there and you get that endpoint's answer (404). It returns 415 only when there is no other candidate. A **missing** `Content-Type` passes `[Consumes]`. For a guaranteed 415, check `Request.HasJsonContentType()` in the action or reader.
3. **`[RequestSizeLimit(n)]` can raise a lowered global `KestrelServerOptions.Limits.MaxRequestBodySize`.** Lower the global (64 KiB here) and set the per-action limit on the few endpoints that need more. It applies only if nothing has read the body before the MVC filter, and TestServer doesn't enforce it, so test it on Kestrel.
4. **413 needs a body read.** If a gate (for example a `CanWrite` 403) runs before the read, an oversized body gets the gate's answer. Order the tests accordingly.
5. **No request decompression by default.** A `Content-Encoding: gzip` body is read raw. Keep it that way (no `UseRequestDecompression`), so there's no zip-bomb path.
6. **`RateLimiterOptions.RejectionStatusCode` defaults to 503.** Set 429.
7. **Query model binding hides inputs** (measured by Yoshi, .NET 11, `[ApiController]`). `[FromQuery] string? kind` binds `kind=` and `kind=%20` as `null` (empty-to-null conversion), so "present but empty" looks like "absent"; `kind=a&kind=b` binds the first value. `[FromQuery] int`/`long?` turns `abc` or an over-range literal into MVC's ModelState ProblemDetails 400, not your error body. When a query parameter's absent, empty, repeated and malformed states must answer differently, read `Request.Query` yourself (`StringValues.Count`, ordinal compare, `long.TryParse` with clamping).

## How to probe
`dotnet new web` in the scratchpad. Reproduce the real app's pipeline order and **its catch-all and fallback routes** (a probe without them gave the wrong 415 answer in Phase 3). Run with `ASPNETCORE_ENVIRONMENT=Production`, curl each edge case, and look at the route value's bytes with `xxd`.
8. **MVC's form value providers read the body before your action** (measured by Boo, .NET 11, 2026-11-13). When the request's `Content-Type` is `application/x-www-form-urlencoded` or `multipart/form-data`, `FormValueProviderFactory`/`FormFileValueProviderFactory` read and parse the whole body during model binding, on **any** action with a parameter (a bare `CancellationToken` or a route value is enough), GETs included. A malformed multipart body or one over the size limit becomes MVC's ProblemDetails **400** before the action, so a service gate (403), a 415 check or a "body read only in the action" rule are all bypassed. Both are CORS-safelisted types, so this is also the shape a Phase 8 CSRF attempt takes. Fix: remove the three form factories (`ValueProviderFactoryExtensions.RemoveType<FormValueProviderFactory|FormFileValueProviderFactory|JQueryFormValueProviderFactory>(options.ValueProviderFactories)`) in a registration shared by Program.cs and every harness. Test the gate with form-typed bodies, not only JSON ones.
9. **Kestrel counts chunked framing toward `MaxRequestBodySize`** (measured, same day). A chunked body a few dozen bytes under the limit gets 413 (with 1,000-byte chunks, 262,000 B against 256 KiB). Only chunked uploads near the limit are affected. Browsers send `Content-Length` for string bodies. Test "exactly at the limit is accepted" with `Content-Length`, and test chunked only well over the limit.
10. **An unread body over `MaxRequestBodySize` kills the keep-alive connection** (measured by Boo, .NET 11, 2026-11-13). Any early response (403, 415, 404, 429) to such a body is followed by Kestrel closing the socket. Without `Connection: close` on the response, a pooling client's next request fails (Python `http.client` 3 of 3; curl silently reconnects, so it can't serve as the repro). Set the header in `OnStarting` when the declared `Content-Length` is over the feature's current `MaxRequestBodySize`. Chunked bodies have no declared length and need a `CanHaveBody` check. Behind a proxy the header is hop-by-hop and protects the proxy's upstream pool.
